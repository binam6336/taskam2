# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Taskam v2 (تسکام) is a Persian (RTL) task/team management panel: plain PHP MVC, no Composer, no build step, no frameworks, no test suite. UI text, comments and commit discussion with the user are in Persian.

## نسخه‌گذاری (الزامی در هر کامیت)
- نسخه‌ی فعلی برنامه در فایل `VERSION` است (Semantic Versioning: MAJOR.MINOR.PATCH).
- در هر کامیت، نسخه را بر اساس نوع تغییر بالا ببرید، فایل `VERSION` را به‌روز کنید و نسخه را ابتدای عنوان کامیت بنویسید، مثل: `v2.1.0: ...`
  - **PATCH** (2.0.0 → 2.0.1): رفع باگ، اصلاح ظاهری یا متنی، بدون قابلیت جدید.
  - **MINOR** (2.0.0 → 2.1.0): قابلیت جدید یا تغییر سازگار با قبل (از جمله migration افزایشی دیتابیس).
  - **MAJOR** (2.0.0 → 3.0.0): تغییر ناسازگار (شکستن API، حذف قابلیت، تغییر ساختار دیتابیس که مهاجرت دستی می‌خواهد).
  - تغییرات فقط مستندات/ابزار که روی برنامه اثری ندارند نسخه را بالا نمی‌برند؛ عنوان کامیت همان نسخه‌ی فعلی را دارد.
- در هر کامیتی که نسخه را بالا می‌برد، تغییرات همان نسخه را به فارسی و به زبان کاربر (نه جزئیات فنی) در بالای `docs/changes.md` بنویسید: `## X.Y.Z — تاریخ شمسی` و فهرست تغییرات.
- **مستندات پنل (پنل مدیر ← تنظیمات ← مستندات پنل، `/admin/docs`)** از `app/Services/PanelDocs.php` ساخته می‌شود. هر تغییری در محدودیت‌ها و قواعد مهم (سقف‌های `Throttle::attempt`/`rateLimit`، سهمیه و حجم آپلود، تلاش ناموفق ورود و قفل حساب، نشست، توکن API، اعلان، دسترسی‌ها) یا اضافه شدن مورد مهم جدید، باید در همان کامیت در این فایل هم به‌روز شود (کارت/ردیف مربوط). عددها را تا جای ممکن از ثابت‌ها/`.env` بخوانید نه به‌صورت متن ثابت.

## مستندات دیتابیس (الزامی در هر تغییر دیتابیس)
- مستندات کامل دیتابیس فایل `docs/database.pdf` است (همه‌ی جدول‌ها، ستون‌ها، نوع داده، پیش‌فرض، کلیدها، روابط و فلوی هر بخش).
- **هر تغییری در دیتابیس** (جدول یا ستون جدید، حذف یا تغییر نام، تغییر نوع، مقدار جدید ENUM، ایندکس یا کلید خارجی جدید، تغییر کاربرد یا فلوی یک ستون/جدول) باید **در همان کامیت** در این مستندات هم نوشته شود:
  1. ساختار در `database/schema.sql` (و migration مربوط) به‌روز شود.
  2. توضیح فارسی جدول/ستون و فلوی آن در `bin/db-docs/describe.py` اضافه یا اصلاح شود (عنوان، توضیح، «فلو و قواعد»، توضیح هر ستون؛ جدول جدید در `GROUPS` هم قرار بگیرد).
  3. فایل PDF دوباره ساخته شود: `python3 bin/db-docs/build.py` — اگر جدول یا ستونی توضیح نداشته باشد ساخت متوقف می‌شود و نامش را اعلام می‌کند.
  4. `docs/database.pdf` جدید همراه بقیه‌ی تغییرات کامیت شود.
- حتی اگر فقط رفتار یا فلوی یک ستون در کد عوض شود (بدون تغییر ساختار)، توضیحش در `describe.py` اصلاح و PDF دوباره ساخته شود.

## Running locally
- Requirements: PHP 7.4+ (8.2 recommended) with `pdo_mysql`, `mbstring`, `fileinfo`, `gd` (+ `openssl` for Web Push); MySQL 5.7+/MariaDB 10.3+.
- Setup: `cp .env.example .env` (fill `DB_*`, `APP_KEY`), create DB `utf8mb4_unicode_ci`, `mysql taskam < database/schema.sql`, `php bin/create-admin.php 09120000000 "مدیر" "سیستم"`.
- Demo load data (test DB only): `php bin/seed-demo.php --yes` builds a 30-person company over ~6 months (manager 09991867331, 5 team projects marked `[داده‌ی نمونه]` in the description, demo users `0999100xxxx` / `Demo12345`, 700 tasks with full delivery/review lifecycle, events, notes); `--tasks=N --days=N --seed=N`; `--clean --yes` removes it. `php bin/export-demo-sql.php > demo-data.sql` exports it as an id-independent SQL file (users matched by mobile via INSERT IGNORE, LAST_INSERT_ID links; deletes previous demo data first) for phpMyAdmin import on a 4.1+ schema. Inserts directly (no notifications); keep it in sync when task lifecycle columns change.
- Source zip for sharing: `sh bin/package.sh` (git archive; never zip the working dir). Migrations without web ALTER rights: `SCHEMA_AUTO=false` + `php bin/migrate.php` (prints each step, re-applies when `Schema::missing()` finds absent columns even if the flag file exists; `--force` ignores flags). Schema errors go to `storage/logs` + `storage/cache/schema-errors.json` (shown in PanelDocs); a PDO «unknown column/table» error deletes the schema flag so the next web request re-runs `Schema::ensure`.
- Dev server: `php -S 127.0.0.1:8080 -t public router.php`, where `router.php` serves existing files under `public/` and otherwise sets `$_SERVER['SCRIPT_NAME'] = '/index.php'` and requires `public/index.php` (there is no router file in the repo; Apache uses `.htaccess`).
- Syntax check: `php -l <file>` for PHP, `node --check <file>` for JS. Verification is done by driving the app in a browser (Playwright), not unit tests.
- Never commit `.env` or `storage/vapid.json`.

## Architecture
Request flow: `public/index.php` → `App::run()` (security headers, session) → `Router` (routes in `config/routes.php`, middleware groups `guest`, `auth`, `authany`, `panel`, `admin`, `csrf` (automatic for web POST), `api`) → Controller → Service → Model → View or JSON. See `docs/ARCHITECTURE.md`, `docs/SECURITY.md`, `docs/DEPLOY.md`.

- **Services are shared by the web panel and the REST API** (`app/Controllers/Api/V1/*`). Business rules live once in a Service and return `['ok','message','code','http','data']` (`res(...)`); web controllers call `$this->respond(...)` (JSON for AJAX, flash+redirect otherwise), API controllers map via `ApiController::fromService` (http 422 → 400).
- **`app/Services/Access.php`** is the single place for permission decisions (creator / assignee / project member perms, task perms, board perms). Don't re-implement checks in controllers.
- **API docs are generated**: `config/api_spec.php` (endpoints/examples) + `config/api_fields.php` (field descriptions) drive both the `/docs` page and `GET /api/v1/`. Any API change must update these.
- **Database changes**: add `database/migrations/NNN_*.sql`, update `database/schema.sql`, and register the column/table in `app/Core/Schema.php` (`COLUMNS`/`TABLES`, bump `VERSION`) — it auto-applies missing additive changes at runtime and writes a flag file to `storage/cache/schema-NNN`. Also add Persian descriptions/flow for new tables/columns in `bin/db-docs/describe.py` and rebuild the database PDF `docs/database.pdf` with `python3 bin/db-docs/build.py` (it fails listing anything undocumented).
- **Public IDs (v5.0, `app/Core/Pid.php`)**: numeric DB ids never leave the server. Every exposed table (`Pid::TABLES`) has a unique `pid` CHAR(12) (random, `[2-9a-hjkmnp-z]`, at least one letter); FKs stay numeric. `DB::insert` fills it; raw `INSERT` into those tables must pass `Pid::new()`; old rows get it in `Schema::ensure`/`migrate.php` (`Pid::backfill`) or lazily in `Pid::of`. Input: route params named in `Pid::ROUTE` (`{task}`, `{project}`, `{user}`, `{label}`, `{note}`, `{ticket}`, `{token}`, `{colreq}`, `{projreq}` — never `{id}` for these) are resolved in `Router` (unknown/numeric = 404); request fields in `Pid::INPUTS` (`user_id`, `project_id`, `assignee_id`, `members[]`, `project`, `label`, …) are translated in `Request` (invalid = `-1`); other ids (API `id` → `ApiController::id()` with `TABLE`, comma lists, cursors) via `Pid::id/ids`. Output: views use `pid('table', $rowOrId)`; JSON/boot/`json_html` pass through `Pid::out` (keys in `Pid::OUTPUTS`/`OUTPUT_LISTS` like `*_id`, `members`, `me` are converted, a row with both `id` and `pid` gets id=pid) but a bare `id` key must be converted explicitly (`pid()`, `Pid::tag($data, 'tasks')`); with `APP_DEBUG` a leaked numeric `id` is logged to `storage/logs/pid-leak.log`. In JS ids are strings: never `Number()`/`+` them, compare with `String()`.
- **Admin-editable content** lives in `content_texts` (key/body) with defaults in config: tour texts (`config/tour_texts.php`, `ContentModel`) and the user-panel sidebar layout (`config/sidebar.php`, `SidebarModel`, key `sidebar.user`). The user sidebar menu is built from `SidebarModel::nav()`, not hard-coded in `layouts/app.php`.
- **User-facing error messages** are catalogued in `config/error_texts.php` (id → group, exact default text, explanation) and admin-editable in «محتوا ← خطاها». `App\Core\ErrorText::apply()` swaps the text by matching the message itself (`{var}` placeholders capture dynamic parts) in `Response::json`, `Session::flash`, `ErrorHandler`, `Uploader` and client-side `TK.toast`. When you add or change an error string in code, add/update its entry there with the exact same text.
- **Input placeholders** in the user panel come from `config/placeholder_texts.php` (id → group, location path, URL, default) and are admin-editable in «محتوا ← Placeholder»: use `ph('id')` in views and `TK.ph('id', 'default')` in JS (overrides reach JS via `boot.ph`). New user-facing placeholders should be added there instead of hard-coded.
- **Security rules (from the v3.25 audit, see `docs/SECURITY.md` §3-1)**: admin roles are `users.admin_role` (`Auth::ADMIN_ROLES`: super «مدیر کل», internal «مدیر داخلی», support «پشتیبان»; first admin is always super, `Auth::adminRole()`); for now every role gets all `Auth::ADMIN_PERMS` (`adminPermissions`) until role-based restriction is added — `users.admin_permissions` is deprecated; only the original super admin account and one's own account are protected from others; admin users list rows have a ⋮ menu (`.u-menu`, details/edit/delete) and «جزئیات» (`GET /admin/users/{id}/details|tasks`, `modules/admin_list.js`) whose project/task clicks impersonate with `to` (only `/tasks|/board|/projects` paths) to open that page. **Impersonation (v5.1, `App\Core\Impersonation`, table `impersonations`) opens the user panel in a new tab under `/as/<token>/…` and never changes the admin session**: `Request::path()` strips the prefix, `Impersonation::boot` (App::run) validates token + session secret `imp_sk` + UA + admin/target state + idle/max TTL or renders a closed page; `base_url()`/`url()` include the prefix, `app_base()` doesn't (assets, `full_url`, admin links); `Auth::user()` = target inside a window, `Auth::realUser()` = admin; session data is scoped per window (`Session::scope`, root keys read-only). Start via `TK.impersonate(userPid, to)` / `[data-impersonate]` (no password since v5.2, opens tab); everything done inside a window is logged by `App\Core\AdminLog` (table `admin_logs`, page `/admin/security` «تنظیمات ← امنیت»): enter/exit from `Impersonation::start/end`, and every INSERT/UPDATE/DELETE on `AdminLog::TRACK` tables captured in `DB::run`/`DB::insert` with before/after row snapshots (new tables a user can change must be added to `TRACK`, column labels to `LABELS`); `/admin/impersonations` lists/ends windows; exit/logout inside a window end only that window (project details popup «ورود به پروژه» → creator's `/projects?focus=ID`, card `.proj-focus`); the creator also has a `project_members` row, so member counts use `pm.user_id <> p.user_id` + 1; `users.last_active_at` = user's own last panel request (Authenticate, every 5 min, not during impersonation); sensitive account actions call `denyImpersonation()`; completing a project task goes through `BoardService::move` (board step perms + column limits); colleague adds are always request-based (only exception: the target already has an approved colleague row for the actor); users can drop themselves from others' lists (`ColleagueService::removeFollower`, tab «کاربرانی که مرا همکار کرده‌اند»); mobiles/emails shown to people without consent go through `mask_mobile()`; web push endpoints must pass `Push::allowedEndpoint()`; heavy panel routes call `$this->rateLimit()`; user uploads pass `$uid` to `Uploader::saveAttachment()` (daily quota); `Throttle::attempt` is hit-then-count; sessions start lazily (only with a session cookie or on first write) and are stored in the `user_sessions` table by `DbSessionHandler` (SHA-256 of the id only), bound at login to the device's IP prefix and browser (`Auth::sameNetwork`, `SESSION_IP_BIND`); client IP comes from proxy headers only via `Request::fromTrustedProxy()` (`TRUSTED_PROXY`=cloudflare|true + `TRUSTED_PROXY_IPS`); project tasks can only be assigned to members of that project. v3.44 audit: blocking goes through `ColleagueService::block` (anyone can be blocked; the blocked list shows user info only for colleagues in either direction, others as «کاربر ناشناس» with `is_hidden`; removes pending requests; blocked pairs can't assign/invite/chat/notify); project role perms apply only to tasks the member sees on the board (`Access::taskPerms` + `canBoardView`); API/JSON outputs whitelist fields (no raw `a.*` rows); throttles keyed by IP use `Request::rateIp()`; creation endpoints call `Limits::create()`; admin changing a user's password/mobile needs the admin's own password. Fonts/icons are self-hosted in `public/assets/vendor`; CSP is `style-src 'self'` with no 'unsafe-inline': never write `style="…"` in views/JS templates — use classes or `data-css="prop:value"` (applied by `TK.applyCss`/MutationObserver in app.js, allowlisted properties, no url()); pages without app.js (error/offline) must use classes only. Session on a new network (same browser) → `Auth::needsReauth()` + `/reauth` password page (API 401 `REAUTH_REQUIRED`); profile lists active sessions. All runtime DDL lives in `Schema` only. Login has an image captcha (`App\Core\Captcha`, `GET /captcha`, uppercase-only, one-time; `CAPTCHA_LOGIN=false` in local `.env` for Playwright tests).
- Layouts: `app/Views/layouts/app.php` (user panel), `admin.php` (admin panel), both render `partials/sidebar.php` (v5.8: skip link, `aside#sidebar` with `.sb-top` brand + rail button, `.sb-tools` search/palette (no new-task button since v5.8.1; the palette still offers «ثبت تسک جدید» = `.qa-fab`), flat `.sb-list` of `.sb-it` links/group buttons, one `.sb-pop` dialog per group with a description under each name (v5.9: admin-editable per item/group as `desc` in the `sidebar.user` JSON via «محتوا ← سایدبار»; missing `desc` = default from `config/sidebar.php` `desc`; display toggle `show_desc` in content key `sidebar.user.opts`, `SidebarModel::options()`; `nav()` returns `desc` on each item), `.sb-me` user card + logout, `dialog.sb-palette` for Ctrl/⌘+K; behaviour in the «سایدبار v5.8» block of app.js; rail state `html.sb-rail` from localStorage `tk.sb.rail`, applied before render by `assets/js/rail.js` in head; no `role=menu`). Page key (`'page' => ...` in controller view meta) drives the active menu item, badges and `boot.live.scope`.
- **Departments / groups (v5.10, «دپارتمان / گروه», page `/groups`, `GroupController` + `GroupService` + `GroupModel`, migration 035)**: `project_groups` (per project, optional `head_id`), `project_group_members` (only members of that project), `task_group_ticks` (each member's «انجام دادم» tick). Managed by the project creator or `add_member` holders; leaving/removal from a project calls `GroupService::onMemberLeft`. A task can be assigned to a group (`tasks.assignee_group_id`, then `assignee_id` = NULL; form value `g:<pid>` in the assignee rselect → hidden `assignee_group_id`) with optional `group_head_approval` (only if the group has a head). `Access::isAssignee()` treats group members as the assignee everywhere (perms, board view, deliver); «mine» queries use `TaskModel::mine($uid)` (assignee OR group member SQL). With head approval a member's tick only toggles their row (`TaskService::toggle`, `effective()['member_tick']`) and `BoardService::groupHeadError` blocks members from moving it to review/done; the head's tick = normal `deliver` (approver → done, else review). Ticks are cleared when the task returns from review/done or is reassigned. KPI (`TaskAnalytics::project`) counts group tasks only as a group row (`is_group`). Notifier sends assignment/rework to all members. A group with tasks can't be deleted. The `/groups` page lists groups of all the user's projects (filter `project`, search `q`); «گروه جدید» is two-step (v5.11): modal `#m-group-proj` picks a project (only `GroupService::canManage` ones), then `#m-group` loads its members with avatars from `GET /groups/members?project=` (checkbox = member, crown radio `head_id` = the single head); delivery flow is fixed since v5.13 (migration/data 037): with a head (live `GroupModel::headOf`) only the head's tick delivers, without a head the task goes to review only when all members ticked (`GroupModel::allTicked`; last tick, own or via group-tick, auto-delivers through `TaskService::groupAutoDeliver`; `groupHeadError` → `GROUP_ALL_REQUIRED` blocks board moves before that); `tasks.group_head_approval` is only a mirror of «group has a head» (input ignored, form shows `#grp-flow-note`); rework of a group task can clear only chosen members (`rework_present` + `rework_members[]` → `BoardService::$reworkOnly`); member list group 7 «منتظر بقیه‌ی گروه» via `TaskModel::groupSql($uid)` + `my_group_tick`, count `*_waitgroup`; dashboard `BoardService::waiting()['headwait']`; KPI `group_ticks` per member and `few` for groups under `TaskAnalytics::GROUP_MIN_TASKS`; removing members warns via `POST /groups/{group}/impact`; `/tasks?new=1&project=&assign=g:<pid>` opens the prefilled form; task list filter `group`. New pages added to `config/sidebar.php` are inserted into saved admin layouts via `SidebarModel::NEW_PAGES` until the admin saves again (`known_pages` in `sidebar.user.opts`).

## Frontend conventions
- One stylesheet `public/assets/css/app.css` (design tokens on `:root`; light theme overrides under `html[data-theme="sage"]` — check new UI in both themes, themes defined in `config/themes.php`).
- One core script `public/assets/js/app.js` exposing the `TK` namespace (`TK.http/post/get`, `TK.toast`, `TK.modal`, `TK.confirm`, `TK.rselect`, AJAX forms via `form[data-ajax]` + `tk:done` event, `TK.after` with `data-after`, live refresh of `[data-live]` regions). Per-page modules in `public/assets/js/modules/`, added from a view with `$this->scripts[] = 'name'`; server data is passed through `$this->boot[...]` and read with `TK.boot()`.
- Strict CSP (`script-src 'self'`): no inline scripts or inline event handlers. Escape dynamic text with `e()` in PHP and `TK.esc()` in JS.
- **Soft navigation (no full reloads) in the user and admin panels** (`TK.visit` in app.js, active when `<body data-layout>` is set): internal links and GET forms fetch the next page, swap `<body>`, re-run `widgets.js` + page modules and dispatch `tk:ready`; links are prefetched on hover. Rules for page modules: keep code inside `tk:ready` or an IIFE (no top-level `const/let`, scripts are re-executed); listeners on `document`/`window` and `setInterval`s created by modules are removed automatically when leaving the page, and any `TK.*` a module overrides (e.g. `TK.reload`) is restored. Things on core elements that must re-run after a swap go in `TK.afterSwap`. Use `TK.visit(url)` instead of `location.href` for in-panel redirects; add `data-no-nav` to links/forms that must do a full load. Different layout, new app.js version, redirects or errors fall back to a normal load. The thin green top bar is `TK.progress`.
- Onboarding tour: `public/assets/js/modules/tour.js` (numbered `STEPS`, display order in `ORDER`, state stored in `users.tour`: NULL = not asked, `skip`, `done`, or step number; form fields targeted via `data-tour="..."` attributes). Step numbers are persisted, so never renumber or reuse one (16 was the old end-of-tour state; «گزینه‌های بیشتر» is 17); texts per step live in `config/tour_texts.php` (`step_N`).
- Board statuses (`BoardService::STATUSES`): rework («بازبینی مسئول», first; next step = backlog via `to_todo`) → backlog → todo → in_progress → review («بررسی سرپرست») → done (rework: supervisor returns a reviewed task, reason stored in `blocked_reason`; the old side column blocked was removed in v4.0). review→rework and any move out of done need `to_done`, rework→review `to_review` (`Access::boardMovePerm`). Role «عضو» gets `Access::MEMBER_BOARD` (all board moves except `to_done`/`move_any`). One-time data fixes go in `Schema::DATA` (flag `storage/cache/data-<id>`). Entering review notifies `BoardService::reviewers()` (bot chat), rework notifies the assignee and adds a task note (author = the returner) with the reason; both feed the dashboard «منتظر اقدام» via `BoardService::waiting()`. Column order per user: `users.board_order` (null = `BoardService::DEFAULT_ORDER`: rework, backlog, todo, in_progress, review, done, archived — `STATUSES` follows it), read via `BoardService::order()`, saved by `POST /board/order` (arrange mode in board.js). New ENUM values go in `Schema::ENUMS`.
- Task due date+time is one field: `TK.duepicker` (widgets.js; quick today/tomorrow/day-after with preset times + custom view), exposing `.date`/`.time` with the datepicker/timepicker interface. Tour step 13 (old separate time step) is no longer in `ORDER`.
- Task form: only title/description/project/assignee are visible; the rest sits in `#task-more` behind `[data-more-toggle]`. Labels are optional (new users get `SubjectModel::DEFAULTS`). File inputs use the icon button `.file-pick` (hidden input inside a label + `[data-file-names]`, handled in app.js).
- Forms in modals marked `data-guard` (task, text, call, ticket) ask before closing with unsaved changes (`TK.modal.tryClose`; Esc/backdrop/`[data-close]` go through it).
