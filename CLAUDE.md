# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Taskam v2 (تسکام) is a Persian (RTL) task/team management panel: plain PHP MVC, no Composer, no build step, no frameworks, no test suite. UI text, comments and commit discussion with the user are in Persian.

## نسخه‌گذاری (الزامی در هر کامیت)
- نسخه‌ی فعلی برنامه در فایل `VERSION` است (Semantic Versioning: MAJOR.MINOR.PATCH).
- در هر کامیت، نسخه را بر اساس نوع تغییر بالا ببرید، فایل `VERSION` را به‌روز کنید و نسخه را ابتدای عنوان کامیت بنویسید، مثل: `v2.1.0: ...`
  - **PATCH** (2.0.0 → 2.0.1): رفع باگ، اصلاح ظاهری یا متنی، بدون قابلیت جدید.
  - **MINOR** (2.0.0 → 2.1.0): قابلیت جدید یا تغییر سازگار با قبل (از جمله migration افزایشی دیتابیس).
  - **MAJOR** (2.0.0 → 3.0.0): تغییر ناسازگار (شکستن API، حذف قابلیت، تغییر ساختار دیتابیس که مهاجرت دستی می‌خواهد).
  - تغییرات فقط مستندات/ابزار که روی برنامه اثری ندارند نسخه را بالا نمی‌برند؛ عنوان کامیت همان نسخه‌ی فعلی را دارد.
- در هر کامیتی که نسخه را بالا می‌برد، تغییرات همان نسخه را به فارسی و به زبان کاربر (نه جزئیات فنی) در بالای `docs/changes.md` بنویسید: `## X.Y.Z — تاریخ شمسی` و فهرست تغییرات.
- **مستندات پنل (پنل مدیر ← تنظیمات ← مستندات پنل، `/admin/docs`)** از `app/Services/PanelDocs.php` ساخته می‌شود. هر تغییری در محدودیت‌ها و قواعد مهم (سقف‌های `Throttle::attempt`/`rateLimit`، سهمیه و حجم آپلود، تلاش ناموفق ورود و قفل حساب، نشست، توکن API، اعلان، دسترسی‌ها) یا اضافه شدن مورد مهم جدید، باید در همان کامیت در این فایل هم به‌روز شود (کارت/ردیف مربوط). عددها را تا جای ممکن از ثابت‌ها/`.env` بخوانید نه به‌صورت متن ثابت.

## مستندات دیتابیس (الزامی در هر تغییر دیتابیس)
- مستندات کامل دیتابیس فایل `docs/database.pdf` است (همه‌ی جدول‌ها، ستون‌ها، نوع داده، پیش‌فرض، کلیدها، روابط و فلوی هر بخش).
- **هر تغییری در دیتابیس** (جدول یا ستون جدید، حذف یا تغییر نام، تغییر نوع، مقدار جدید ENUM، ایندکس یا کلید خارجی جدید، تغییر کاربرد یا فلوی یک ستون/جدول) باید **در همان کامیت** در این مستندات هم نوشته شود:
  1. ساختار در `database/schema.sql` (و migration مربوط) به‌روز شود.
  2. توضیح فارسی جدول/ستون و فلوی آن در `bin/db-docs/describe.py` اضافه یا اصلاح شود (عنوان، توضیح، «فلو و قواعد»، توضیح هر ستون؛ جدول جدید در `GROUPS` هم قرار بگیرد).
  3. فایل PDF دوباره ساخته شود: `python3 bin/db-docs/build.py` — اگر جدول یا ستونی توضیح نداشته باشد ساخت متوقف می‌شود و نامش را اعلام می‌کند.
  4. `docs/database.pdf` جدید همراه بقیه‌ی تغییرات کامیت شود.
- حتی اگر فقط رفتار یا فلوی یک ستون در کد عوض شود (بدون تغییر ساختار)، توضیحش در `describe.py` اصلاح و PDF دوباره ساخته شود.

## Running locally
- Requirements: PHP 7.4+ (8.2 recommended) with `pdo_mysql`, `mbstring`, `fileinfo`, `gd` (+ `openssl` for Web Push); MySQL 5.7+/MariaDB 10.3+.
- Setup: `cp .env.example .env` (fill `DB_*`, `APP_KEY`), create DB `utf8mb4_unicode_ci`, `mysql taskam < database/schema.sql`, `php bin/create-admin.php 09120000000 "مدیر" "سیستم"`.
- Source zip for sharing: `sh bin/package.sh` (git archive; never zip the working dir). Migrations without web ALTER rights: `SCHEMA_AUTO=false` + `php bin/migrate.php`.
- Dev server: `php -S 127.0.0.1:8080 -t public router.php`, where `router.php` serves existing files under `public/` and otherwise sets `$_SERVER['SCRIPT_NAME'] = '/index.php'` and requires `public/index.php` (there is no router file in the repo; Apache uses `.htaccess`).
- Syntax check: `php -l <file>` for PHP, `node --check <file>` for JS. Verification is done by driving the app in a browser (Playwright), not unit tests.
- Never commit `.env` or `storage/vapid.json`.

## Architecture
Request flow: `public/index.php` → `App::run()` (security headers, session) → `Router` (routes in `config/routes.php`, middleware groups `guest`, `auth`, `authany`, `panel`, `admin`, `csrf` (automatic for web POST), `api`) → Controller → Service → Model → View or JSON. See `docs/ARCHITECTURE.md`, `docs/SECURITY.md`, `docs/DEPLOY.md`.

- **Services are shared by the web panel and the REST API** (`app/Controllers/Api/V1/*`). Business rules live once in a Service and return `['ok','message','code','http','data']` (`res(...)`); web controllers call `$this->respond(...)` (JSON for AJAX, flash+redirect otherwise), API controllers map via `ApiController::fromService` (http 422 → 400).
- **`app/Services/Access.php`** is the single place for permission decisions (creator / assignee / project member perms, task perms, board perms). Don't re-implement checks in controllers.
- **API docs are generated**: `config/api_spec.php` (endpoints/examples) + `config/api_fields.php` (field descriptions) drive both the `/docs` page and `GET /api/v1/`. Any API change must update these.
- **Database changes**: add `database/migrations/NNN_*.sql`, update `database/schema.sql`, and register the column/table in `app/Core/Schema.php` (`COLUMNS`/`TABLES`, bump `VERSION`) — it auto-applies missing additive changes at runtime and writes a flag file to `storage/cache/schema-NNN`. Also add Persian descriptions/flow for new tables/columns in `bin/db-docs/describe.py` and rebuild the database PDF `docs/database.pdf` with `python3 bin/db-docs/build.py` (it fails listing anything undocumented).
- **Admin-editable content** lives in `content_texts` (key/body) with defaults in config: tour texts (`config/tour_texts.php`, `ContentModel`) and the user-panel sidebar layout (`config/sidebar.php`, `SidebarModel`, key `sidebar.user`). The user sidebar menu is built from `SidebarModel::nav()`, not hard-coded in `layouts/app.php`.
- **User-facing error messages** are catalogued in `config/error_texts.php` (id → group, exact default text, explanation) and admin-editable in «محتوا ← خطاها». `App\Core\ErrorText::apply()` swaps the text by matching the message itself (`{var}` placeholders capture dynamic parts) in `Response::json`, `Session::flash`, `ErrorHandler`, `Uploader` and client-side `TK.toast`. When you add or change an error string in code, add/update its entry there with the exact same text.
- **Input placeholders** in the user panel come from `config/placeholder_texts.php` (id → group, location path, URL, default) and are admin-editable in «محتوا ← Placeholder»: use `ph('id')` in views and `TK.ph('id', 'default')` in JS (overrides reach JS via `boot.ph`). New user-facing placeholders should be added there instead of hard-coded.
- **Security rules (from the v3.25 audit, see `docs/SECURITY.md` §3-1)**: admin permissions are `Auth::ADMIN_PERMS` (super admin = all; `impersonate`, `edit_content` are separate); sensitive account actions call `denyImpersonation()`; completing a project task goes through `BoardService::move` (board step perms + column limits); colleague adds are always request-based (only exception: the target already has an approved colleague row for the actor); users can drop themselves from others' lists (`ColleagueService::removeFollower`, tab «کاربرانی که مرا همکار کرده‌اند»); mobiles/emails shown to people without consent go through `mask_mobile()`; web push endpoints must pass `Push::allowedEndpoint()`; heavy panel routes call `$this->rateLimit()`; user uploads pass `$uid` to `Uploader::saveAttachment()` (daily quota); `Throttle::attempt` is hit-then-count; sessions start lazily (only with a session cookie or on first write) and are stored in the `user_sessions` table by `DbSessionHandler` (SHA-256 of the id only), bound at login to the device's IP prefix and browser (`Auth::sameNetwork`, `SESSION_IP_BIND`); client IP comes from proxy headers only via `Request::fromTrustedProxy()` (`TRUSTED_PROXY`=cloudflare|true + `TRUSTED_PROXY_IPS`); project tasks can only be assigned to members of that project. v3.44 audit: blocking goes through `ColleagueService::block` (anyone can be blocked; the blocked list shows user info only for colleagues in either direction, others as «کاربر ناشناس» with `is_hidden`; removes pending requests; blocked pairs can't assign/invite/chat/notify); project role perms apply only to tasks the member sees on the board (`Access::taskPerms` + `canBoardView`); API/JSON outputs whitelist fields (no raw `a.*` rows); throttles keyed by IP use `Request::rateIp()`; creation endpoints call `Limits::create()`; admin changing a user's password/mobile needs the admin's own password. Fonts/icons are self-hosted in `public/assets/vendor`; CSP is `style-src 'self'` with no 'unsafe-inline': never write `style="…"` in views/JS templates — use classes or `data-css="prop:value"` (applied by `TK.applyCss`/MutationObserver in app.js, allowlisted properties, no url()); pages without app.js (error/offline) must use classes only. Session on a new network (same browser) → `Auth::needsReauth()` + `/reauth` password page (API 401 `REAUTH_REQUIRED`); profile lists active sessions. All runtime DDL lives in `Schema` only. Login has an image captcha (`App\Core\Captcha`, `GET /captcha`, uppercase-only, one-time; `CAPTCHA_LOGIN=false` in local `.env` for Playwright tests).
- Layouts: `app/Views/layouts/app.php` (user panel), `admin.php` (admin panel), both render `partials/sidebar_nav.php`. Page key (`'page' => ...` in controller view meta) drives the active menu item, badges and `boot.live.scope`.
- Labels were renamed from "subjects": DB table `subjects` and fields `subject_id/subject_title/subject_color` are kept for compatibility, UI says لیبل and the panel URL is `/labels`.

## Frontend conventions
- One stylesheet `public/assets/css/app.css` (design tokens on `:root`; light theme overrides under `html[data-theme="sage"]` — check new UI in both themes, themes defined in `config/themes.php`).
- One core script `public/assets/js/app.js` exposing the `TK` namespace (`TK.http/post/get`, `TK.toast`, `TK.modal`, `TK.confirm`, `TK.rselect`, AJAX forms via `form[data-ajax]` + `tk:done` event, `TK.after` with `data-after`, live refresh of `[data-live]` regions). Per-page modules in `public/assets/js/modules/`, added from a view with `$this->scripts[] = 'name'`; server data is passed through `$this->boot[...]` and read with `TK.boot()`.
- Strict CSP (`script-src 'self'`): no inline scripts or inline event handlers. Escape dynamic text with `e()` in PHP and `TK.esc()` in JS.
- **Soft navigation (no full reloads) in the user and admin panels** (`TK.visit` in app.js, active when `<body data-layout>` is set): internal links and GET forms fetch the next page, swap `<body>`, re-run `widgets.js` + page modules and dispatch `tk:ready`; links are prefetched on hover. Rules for page modules: keep code inside `tk:ready` or an IIFE (no top-level `const/let`, scripts are re-executed); listeners on `document`/`window` and `setInterval`s created by modules are removed automatically when leaving the page, and any `TK.*` a module overrides (e.g. `TK.reload`) is restored. Things on core elements that must re-run after a swap go in `TK.afterSwap`. Use `TK.visit(url)` instead of `location.href` for in-panel redirects; add `data-no-nav` to links/forms that must do a full load. Different layout, new app.js version, redirects or errors fall back to a normal load. The thin green top bar is `TK.progress`.
- Onboarding tour: `public/assets/js/modules/tour.js` (numbered `STEPS`, display order in `ORDER`, state stored in `users.tour`: NULL = not asked, `skip`, `done`, or step number; form fields targeted via `data-tour="..."` attributes). Step numbers are persisted, so never renumber or reuse one (16 was the old end-of-tour state; «گزینه‌های بیشتر» is 17); texts per step live in `config/tour_texts.php` (`step_N`).
- Board statuses (`BoardService::STATUSES`): rework («بازبینی مسئول», first; next step = backlog via `to_todo`) → backlog → todo → in_progress → review («بررسی سرپرست») → done (rework: supervisor returns a reviewed task, reason stored in `blocked_reason`; the old side column blocked was removed in v4.0). review→rework and any move out of done need `to_done`, rework→review `to_review` (`Access::boardMovePerm`). Role «عضو» gets `Access::MEMBER_BOARD` (all board moves except `to_done`/`move_any`). One-time data fixes go in `Schema::DATA` (flag `storage/cache/data-<id>`). Entering review notifies `BoardService::reviewers()` (bot chat), rework notifies the assignee and adds a task note (author = the returner) with the reason; both feed the dashboard «منتظر اقدام» via `BoardService::waiting()`. Column order per user: `users.board_order` (null = `BoardService::DEFAULT_ORDER`: rework, backlog, todo, in_progress, review, done, archived — `STATUSES` follows it), read via `BoardService::order()`, saved by `POST /board/order` (arrange mode in board.js). New ENUM values go in `Schema::ENUMS`.
- Task due date+time is one field: `TK.duepicker` (widgets.js; quick today/tomorrow/day-after with preset times + custom view), exposing `.date`/`.time` with the datepicker/timepicker interface. Tour step 13 (old separate time step) is no longer in `ORDER`.
- Task form: only title/description/project/assignee are visible; the rest sits in `#task-more` behind `[data-more-toggle]`. Labels are optional (new users get `SubjectModel::DEFAULTS`). File inputs use the icon button `.file-pick` (hidden input inside a label + `[data-file-names]`, handled in app.js).
- Forms in modals marked `data-guard` (task, text, call, ticket) ask before closing with unsaved changes (`TK.modal.tryClose`; Esc/backdrop/`[data-close]` go through it). Pages can set `TK.leaveGuard = () => bool` to confirm soft-nav away (profile). `TK.toast(msg, type, ms, {action:{label,onClick}})` supports an action button (task «بازگردانی» via `undo` in the toggle response). Browser validation messages are Persian (app.js `invalid` handler); password inputs get a reveal button, `data-pw-meter` and `data-pw-match="field"` (widgets.js). Charts size their viewBox to the element width so text renders at real size; `TK.charts.line(..., {connect:true})` joins points across gaps. Profile option forms use `data-autosave` + `data-after="none"`. Chat sends with Ctrl+Enter (same as support). Chat «پیام جدید» (pencil `#chat-new`) → `POST /chat/api/start` finds a user by mobile (`ColleagueService::search` rules + `user_lookup` throttle). Free chat (`ChatModel::canChat`) = approved colleague, shared project or accepted `chat_requests`; otherwise one text message creates a pending request (`ChatController::assertReceiver`), the receiver accepts (`POST /chat/api/accept`) or blocks from the banner `#chat-req`. Blocked list hides non-colleagues behind `block_key` (ghost rows for unknown ids). GET routes must not change state (reminders ack via `POST /notifications/ack`).
- `TK.info(message, {title, icon})` shows a simple explanation popup; any element with `data-lock-reason="..."` opens it on click (board lock icon, locked «انتقال به …» in task details — reasons come from `BoardService::lockReason`). Task details have quick-edit chips (`[data-qe]` in tasks.js: priority, board status via `POST /tasks/{id}/status` → `BoardService::setStatus`, label, project, due) gated by `can.*` and `board.targets`. Pages that include `partials/task_modals.php` (tasks, board, calendar, dashboard) open `a[data-open-task]` in place instead of navigating. The bolt FAB (`[data-quick-task]`, `partials/quick_task.php` + `modules/quicktask.js`, loaded on every user-panel page) is «ثبت سریع تسک»: title only, `@` picks the assignee and `#` the project from `GET /tasks/quick-options` (`TaskService::quickOptions`), `POST /tasks/quick` creates with `tasks.is_quick = 1` (default project = `TaskService::defaultProject`); `BoardService::move` resets `is_quick`, and task details show the bolt chip while it is set. The old profile «دسترسی سریع» links (`users.quick_links`) are deprecated.
- **Tick = delivery for review (v4.1)**: the «انجام شد» tick (`TaskService::toggle` → `BoardService::deliver`) moves any project task to `review` for everyone (even admins), allowed by `Access::canDeliver` (assignee, creator, `complete` or board `to_review`); sets `tasks.delivered_at/delivered_by`; the deliverer can undo via `POST /tasks/{id}/withdraw`. `done` is reachable only from `review` (`REVIEW_REQUIRED`) and sets `approved_by`. `TaskService::effective` exposes `deliver/withdraw/approve/rework/tick/status`; task details and dashboard «منتظر اقدام» show «تأیید و بستن» / «برگرداندن برای اصلاح» (`TK.prompt`). KPI (`TaskAnalytics`): assignee time ends at `delivered_at` (`finishedAt`), lateness is day-level (`isLate`), reviewer approval time per `approved_by`. «عقب‌افتاده» = `due_date < CURDATE()` everywhere (`TaskModel::OVERDUE`); today with passed time shows «ساعت گذشته». Task list default sort `smart` (`TaskModel::GROUP_SQL`: no date → today → upcoming → overdue → done, with group headers) with quick chips (`when`, `flow=review|rework`). `TK.rselect` supports `{group}` headers, `note`, `disabled`+`hint`, `setOptions()`; task form assignee list is grouped by project members (non-members → add to project first). Board: empty columns `.kb-collapsed`, start column `data-kb-start` (review for approvers).
- **No deletion for users (v4.0)**: tasks, projects, labels and call requests are never deleted from the user panel/API — they are «مسدود» (`blocked_at`/`blocked_by` columns, `App\Services\BlockService`, routes `POST /block/{kind}/{id}`, `POST /unblock/{kind}/{id}`, `GET /blocked/{kind}` with kind tasks|projects|labels|calls; API `/tasks|labels|calls/block|unblock|blocked`, `/projects/block-project|unblock-project|blocked-projects`). Every list/count/selector query must add `blocked_at IS NULL`; blocked tasks are read-only (`Access::canTask` allows only `view`/`block`, services return `TASK_BLOCKED`). Each page shows `partials/blocked_button.php` opening the shared `#m-blocked` modal (`modules/blocked.js`); task details have a ⋮ menu (block/unblock). Task perm `delete` became `block`; board column/status `blocked` and board perms block/unblock were removed (`blocked_reason` now only holds the rework reason). Notes, attachments, chat messages and tickets have no user delete; only ready texts (plus API tokens and the avatar) can be deleted.
